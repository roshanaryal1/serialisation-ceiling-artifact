# Phase 5 status — harness built, gate met

## Gate (RESEARCH_PLAN.md Phase 5): "harness runs unattended on desktop Chrome and produces valid raw files for one full corpus sweep."

**Met.** `node runner.js --smoke-test` ran unattended (no manual intervention after launch), drove headless Chromium via Playwright, loaded `bench_page.html`, embedded a corpus in-browser with the app's real `@xenova/transformers` install, ran 10 sample queries, and wrote structured JSON matching `MEASUREMENT_PLAN.md`'s metric set. Evidence preserved in `research/harness/smoke_test_output/` (2 runs, corpus_1000, cold cache, 4 threads — NOT a protocol-compliant measurement run, see below).

## What the smoke test proved works

- End-to-end pipeline: static server → Playwright → bench_page.html → `@xenova/transformers` load → corpus embed → query embed+search → JSON written to disk.
- Similarity scores are sane and in the expected range: e.g. query `"Scissor Lift 26' Electric, 29.0 ft"` → top match `synthetic-0000813`, score 0.81 — same order of magnitude as the fp32 Python baseline's ~0.88 for the equivalent case, with the gap being exactly the kind of quantisation delta RQ1 is measuring. This is a good sign the pipeline isn't producing garbage, though it is not itself a validated RQ1 number (that requires the full protocol, qrels, and cross-referencing against `baseline/dense_top50_*.json`).
- Cold-cache isolation works at three layers, not just one: `instrument.js`'s `clearAllStorage()` empties Cache API + IndexedDB in-page (`storage_cleared: {caches: 0, indexedDB: 0}`), `runner.js` additionally gives every cold repeat a brand-new isolated `BrowserContext` (so no leftover state from a prior page load in the same context) and disables the browser's regular HTTP disk cache via CDP (`Network.setCacheDisabled`) before navigation. The third layer was added after the first smoke test attempt showed suspiciously low transfer bytes on a nominally "cold" run — see item 3 below. Warm cells intentionally reuse one shared context across repeats so Cache API state genuinely persists, matching what "warm" means.
- Explicit thread count honoured: `threads_configured: 4` and `threads_actual_reported: 4` match.
- Chromium JS heap capture works: 131,000,000 bytes reported for a 1k-corpus cold run.

## Known limitations, stated now rather than discovered mid-Phase-7

1. **WASM heap is `null`.** `onnxruntime-web` (bundled inside `@xenova/transformers@2.17.2`) doesn't expose its `WebAssembly.Memory` instance through a stable public API in this version — `instrument.js`'s `getWasmHeapBytes()` checks the one place it's sometimes been observed and returns `null` otherwise, rather than fabricating a number. JS heap (Chromium-only) is the practical proxy available right now. If WASM heap turns out to matter for the memory-ceiling finding on the 8GB Mac (`MEASUREMENT_PLAN.md` amendment 2), this needs a real fix — likely patching in a JS heap snapshot via a different library entry point, or accepting JS-heap-only for that finding and saying so.
2. **`model_load` is one combined span**, not decomposed into transfer/WASM-init/tokenizer-init as `MEASUREMENT_PLAN.md`'s cold-start table wants. `@xenova/transformers`'s `pipeline()` call doesn't expose intermediate hooks publicly. Transfer bytes ARE independently recoverable via Resource Timing (`model_transfer_bytes`) and are captured separately, so partial decomposition exists; full decomposition may need monkey-patching `env`/fetch or is simply not achievable with this library version — to be revisited if the paper needs the full breakdown and not just transfer bytes + combined load time.
3. ~~`model_transfer_bytes` looked low (2.36MB vs ~22MB expected)~~ — **RESOLVED.** Root cause: the model is fetched from `huggingface.co`'s CDN by default, a cross-origin request, and the Resource Timing API zeroes out `encodedBodySize`/`transferSize` for cross-origin resources unless the server sends a `Timing-Allow-Origin` header (HF's CDN doesn't). The regex was accidentally matching an unrelated same-name-pattern `ort-wasm-simd.wasm` runtime file fetched from `cdn.jsdelivr.net` instead. Fixed by mirroring the model files (already present locally from the earlier `npm run embeddings` run) under `research/harness/models/` and setting `env.allowRemoteModels = false` / `env.localModelPath` in `bench_page.js` so everything loads same-origin — Resource Timing then reports full, accurate sizes. Verified: `model_quantized.onnx` now reports exactly 22,972,370 bytes, matching `PROVENANCE.md`'s recorded file size and SHA-256 exactly. Bonus: this also makes network-profile throttling (a separate Phase 5 protocol requirement) tractable, since it no longer depends on a live third-party CDN's actual behavior.
4. **Index build embeds the entire corpus in-browser** (23.5s for 1,000 docs in the smoke test) — this is the documented divergence from the real app path (see `bench_page.html`'s own comment): the real app ships precomputed vectors and never does this. Confirms this will be a real, possibly dominant cost at 100k+ corpus sizes — relevant to RQ2.
