# Corpus generation report (Phase 2)

Generated by `generate_corpus.py --seed 42`. Regenerate anytime — deterministic.

## Strict superset property

Verified by exact `diff` of the first N lines of `corpus_500000.jsonl` against
each smaller corpus file — `corpus_1000.jsonl`, `corpus_10000.jsonl`,
`corpus_100000.jsonl`, and `corpus_250000.jsonl` are each an exact line-for-line
prefix of `corpus_500000.jsonl`. Confirmed, not assumed.

**Assessment**: the two corpora that matter for RQ1 (quality) — 1k and 10k, since
Phase 3's 250-query/qrels set is built over the 10k corpus per the plan — have a
low-to-negligible exact-duplicate rate (0%, 0.66%). 100k (used for RQ2 scaling,
not for quality judgments) is at 5.4%, non-trivial but not dominant.

The 250k/500k reserve arms have a materially higher duplicate rate (12-21%)
because the templated vocabulary's combinatorial capacity is finite and these
sizes were explicitly out-of-scope unless Phase 6's pilot triggers the
"reframed contribution" path (RESEARCH_PLAN.md Phase 6). **If Phase 6 selects
that path, the vocabulary in `generate_corpus.py` (types/modifiers/spec
ranges per category) needs expanding before those corpora are used for any
reported measurement** — this is flagged now so it isn't discovered mid-Phase-7.
Not fixed pre-emptively because expanding vocabulary for scales that may never
be used would be premature effort against the plan's own conditional gate.

## Near-duplicate distribution (Jaccard similarity, bag-of-words, sampled pairs)

Via `check_near_duplicates.py`, ~20,000 random pairs per corpus, seed 1234.
Random-pair sampling under-detects rare exact duplicates (a 0.66% exact-dup
rate at n=10,000 means ~66 exact-dup pairs out of ~50M possible pairs — a
20k random sample is unlikely to hit one), so this measures the *general*
content-similarity distribution, not the exact-duplicate rate above; both are
reported because they answer different questions (the plan asks for both:
"guarantee no near-duplicates... and check pairwise similarity... report the
distribution").

| Corpus | p50 | p90 | p95 | p99 | max | pairs Jaccard≥0.8 (of ~20k sampled) |
|---|---|---|---|---|---|---|
| corpus_1000 | 0.115 | 0.174 | 0.208 | 0.409 | 0.875 | 5 |
| corpus_10000 | 0.115 | 0.172 | 0.200 | 0.429 | 0.889 | 8 |
| corpus_100000 | 0.111 | 0.172 | 0.200 | 0.409 | 0.889 | 7 |

Similarity is low and flat across corpus sizes (median Jaccard ~0.11-0.12,
99th percentile ~0.41-0.43) — no evidence of systematic near-duplication at
the sizes used for RQ1. High-Jaccard pairs (≥0.8) are rare (≤8 per ~20k
sampled pairs, i.e. ≤0.04%) and expected: same category + same equipment
type + adjacent spec value naturally produces high word overlap in a
templated corpus, which is a known property of templated generation
(RESEARCH_PLAN.md Phase 2 honesty requirement), not a generation bug.

## Known cosmetic issue (not fixed, documented)

`generate_corpus.py`'s article correction ("a" -> "an") checks the first
*letter* of the equipment type, not its phonetic sound, so it incorrectly
emits "an utility trailer" and similar (u/eu-initial words with a consonant
sound). Cosmetic only — does not affect tokenization for the embedding model
in any way that matters for retrieval quality, so not worth fixing before
Phase 3. Flagged so it isn't mistaken for a data-quality bug later.
